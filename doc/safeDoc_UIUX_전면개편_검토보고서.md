# safeDoc UI/UX 전면 개편 검토보고서

- **대상 저장소**: `Ubermensch216/safeDoc`
- **검토 분야**: UI/UX, 정보구조, 메뉴 체계, 화면 배치, 시각 디자인
- **작성일**: 2026-08-04

---

## 1. 검토 개요

safeDoc은 문서 내 개인정보를 로컬 환경에서 탐지하고, 사용자가 검토한 후 비식별 처리하는 개인 PC용 프로그램이다.

주요 업무 흐름은 다음과 같다.

> 문서 선택 → 자동 분석 → 개인정보 후보 검토 → 비식별 처리 → 결과 확인 및 다운로드

현재 프로그램은 개인정보 탐지, 수동 후보 추가, AI 보조 탐지, 처리방식 지정, 결과 비교, 대응표 생성, 원본 복원 등 기능적인 완성도가 높은 편이다. 접근성 측면에서도 키보드 이동, ARIA 속성, 포커스 표시, 다크모드, 동작 축소 설정 등이 비교적 충실하게 구현되어 있다.

다만 현재 UI는 기능을 빠짐없이 화면에 배치하는 데 초점이 맞춰져 있어, 사용자가 실제 업무에서 판단해야 하는 순서와 중요도가 화면에 충분히 반영되지 않는다.

핵심 문제는 다음과 같다.

> 기능은 풍부하지만, 사용자가 무엇을 먼저 확인하고 다음에 무엇을 해야 하는지가 화면 구조만으로 즉시 이해되지 않는다.

따라서 단순한 색상 변경이나 버튼 스타일 개선보다 메뉴 구조, 작업 흐름, 화면 위계, 검토 인터랙션을 포함한 전면적인 개편이 필요하다.

## 2. 종합 평가

### 2.1 잘 설계된 부분

현재 safeDoc의 장점은 다음과 같다.

- 외부 서버로 개인정보를 전송하지 않는다는 신뢰 요소를 지속적으로 표시
- 규칙 기반 탐지와 AI 기반 탐지를 구분
- 후보 목록을 검토 필요도 순으로 정렬
- 키보드를 이용한 후보 이동과 선택 지원
- 후보 필터, 정렬, 일괄 선택, 동일값 일괄 처리 지원
- 문서 미리보기와 개인정보 후보 목록을 동시에 제공
- 긴 문서를 구간별로 검토할 수 있도록 구성
- 라이트모드와 다크모드 지원
- 보조기기용 상태 알림과 WAI-ARIA 탭 패턴 적용
- 색상을 개인정보 유형이 아니라 검토 상태와 위험도에 사용하는 원칙 적용

특히 AI 단독 발견, AI 오탐 의심, 낮은 신뢰도 후보를 먼저 보여 주는 위험도 기반 정렬 방식은 전문 검토 도구의 성격에 적합하다.

### 2.2 전면 개편이 필요한 부분

현재 화면은 개발자 관점에서 기능을 체계적으로 나열한 구조에 가깝다. 그러나 일반 행정 사용자는 다음과 같은 부담을 느낄 가능성이 크다.

- 상단 탭과 작업 단계의 관계를 이해해야 함
- 여러 개의 필터와 도구모음 중 먼저 사용할 것을 판단해야 함
- 체크박스, 처리방식, AI 배지, 신뢰도 등 여러 상태를 동시에 해석해야 함
- 결과 화면에서 어떤 파일을 우선 다운로드해야 하는지 판단해야 함
- 설정 화면에서 일반 설정과 고급 기술 설정을 구분해야 함

전면 개편의 핵심 방향은 다음 세 가지로 정리할 수 있다.

1. **메뉴 중심 구조를 작업 중심 구조로 전환**
2. **개인정보 유형 중심 화면을 검토 상태 중심 화면으로 전환**
3. **모든 기능을 항상 노출하는 방식에서 필요한 순간에만 제공하는 방식으로 전환**

## 3. 현재 정보구조 분석

### 3.1 현재 최상위 메뉴

현재 헤더에는 다음 세 개의 탭이 배치되어 있다.

1. 비식별 처리
2. 원본 복원
3. 설정

비식별 처리 탭 내부에는 다시 다음 네 단계가 표시된다.

1. 문서 선택
2. 분석
3. 검토
4. 결과

즉, 현재 UI에는 다음 두 가지 탐색 체계가 동시에 존재한다.

- 상위 기능 탭
- 비식별 처리 내부의 단계형 흐름

### 3.2 구조적 문제

#### 가. 탭과 작업 단계의 역할 혼재

비식별 처리는 하나의 긴 작업 과정인 반면, 원본 복원과 설정은 독립 기능이다. 그러나 세 기능이 동일한 수준의 탭으로 배치되어 기능 간 중요도와 사용 빈도가 제대로 드러나지 않는다.

작업 도중 복원이나 설정 탭으로 이동할 수 있어 현재 작업의 맥락이 끊길 가능성도 있다.

#### 나. 단계 표시의 반복

문서 선택, 분석, 검토, 결과 단계가 각 화면에 반복적으로 표시된다. 일관성은 있으나 검토 화면처럼 세로 공간이 중요한 화면에서도 단계 표시가 자리를 차지한다.

#### 다. 설정 화면의 평면적 구성

AI 설정, 유형별 처리방식, 사용자 정규식 규칙은 사용 빈도와 난이도가 다르지만 현재 동일한 패널 수준으로 나열되어 있다.

- AI 엔진 주소와 모델은 주로 설치·관리 단계에서 사용
- 유형별 처리방식은 업무 정책에 해당
- 사용자 정규식은 고급 사용자 기능

이들을 기본 설정과 고급 설정으로 구분할 필요가 있다.

## 4. 화면별 UI/UX 진단

## 4.1 시작 화면

현재 시작 화면은 다음 순서로 구성된다.

- 진행 단계
- 문서 업로드 영역
- 작동 방식 설명
- 개인정보 보호 설명
- 주의사항

### 장점

- 지원 파일 형식과 최대 용량이 명확함
- 로컬 처리라는 핵심 신뢰 요소가 잘 설명됨
- 자동 탐지의 한계와 지원 제외 문서를 숨기지 않음
- 문서 선택 영역이 충분히 큼

### 문제점

#### 설명 정보가 행동보다 크게 보임

사용자의 첫 번째 목적은 문서를 선택하는 것이다. 그러나 업로드 영역 아래 세 개의 설명 카드가 넓은 면적을 차지한다.

초회 사용자에게는 도움이 되지만 반복 사용자는 매번 동일한 설명을 보게 된다.

#### 다음 과정이 한눈에 보이지 않음

사용자는 파일을 올리기 전 다음 내용을 알고 싶어 한다.

- 원본 파일이 유지되는가
- 자동으로 바로 변경되는가
- 중간 검토가 가능한가
- AI 없이도 동작하는가
- 최종 결과가 어떤 형태로 제공되는가

현재 설명 카드에 내용이 포함되어 있으나 짧은 작업 흐름으로 시각화되어 있지 않다.

#### 경고가 지나치게 강함

첫 화면의 강한 경고 카드는 프로그램이 위험하거나 불안정하다는 인상을 줄 수 있다. 중요한 경고는 유지하되, 기본 화면에서는 핵심 내용만 보여 주고 상세 내용을 접기·펼치기로 제공하는 편이 좋다.

## 4.2 분석 화면

현재 분석 화면은 다음 항목으로 구성된다.

- 분석 중이라는 제목
- 파일 정보
- 진행 막대
- 분석 상태 문구
- 분석 취소 버튼

### 장점

구성이 단순하고 집중도가 높다.

### 문제점

실제 분석 과정은 파일 읽기, 텍스트 추출, 규칙 탐지, AI 탐지 등 여러 단계로 나뉘지만 사용자에게는 하나의 진행 막대로만 보인다.

따라서 사용자는 다음 상태를 구분하기 어렵다.

- 분석이 멈춘 것인지
- 규칙 탐지가 끝난 것인지
- AI 탐지가 진행 중인지
- AI 엔진을 사용할 수 없어 건너뛴 것인지

### 개선 방향

퍼센트 중심 진행 막대 대신 단계별 체크리스트를 권장한다.

```text
✓ 파일 열기
✓ 텍스트 추출
✓ 규칙 기반 탐지
● AI 추가 탐지
○ 검토 화면 준비
```

AI 탐지는 선택 기능이므로 규칙 기반 결과가 준비되면 사용자가 먼저 검토 화면으로 이동할 수 있도록 하는 것이 좋다.

## 4.3 검토 화면

검토 화면은 safeDoc에서 가장 중요한 화면이며 개선 필요성도 가장 크다.

현재 구조는 다음과 같다.

- 진행 단계
- 문서 정보
- AI 진행 상태
- 유형별 필터 칩
- 필터 일괄 작업 영역
- 왼쪽 문서 미리보기
- 오른쪽 개인정보 후보 목록
- 검색 및 수동 지정 도구
- 전체 선택·해제·되돌리기
- 정렬 기준
- 키보드 힌트
- 실행 전 확인 체크박스
- 비식별 실행 버튼

### 장점

- 문서와 후보를 좌우로 배치한 기본 방향은 적절함
- 검토 필요도가 높은 후보를 먼저 보여 줌
- AI 발견, AI 확인, 오탐 의심을 구분함
- AI 결과가 추가되어도 스크롤과 펼침 상태를 유지함
- 직접 선택, 문자열 검색, 동일값 일괄 처리 기능이 있음

### 핵심 문제 1. 도구모음 과다

검토 화면에는 다음 조작 영역이 여러 층으로 배치되어 있다.

1. 유형별 필터
2. 필터 대상 일괄 작업
3. 미리보기 도구
4. 문자열 검색 및 지정
5. 전체 선택·해제·되돌리기
6. 정렬
7. 키보드 안내
8. 실행 전 확인
9. 실행 버튼

초보자는 각 영역의 역할을 구분하기 어렵다.

특히 다음 항목은 의미가 혼동될 수 있다.

- 전체 선택이 전체 문서 기준인지 현재 필터 기준인지
- 지정과 선택 영역 추가의 차이
- 체크박스와 처리방식 선택의 관계
- 필터 해제와 후보 제외의 차이

### 핵심 문제 2. 후보 카드의 정보 과밀

후보 카드 한 줄에는 다음 정보가 동시에 표시된다.

- 처리 대상 체크박스
- 개인정보 원문
- 개인정보 유형
- AI 출처
- AI 판단 근거
- 처리방식 선택
- 상세 펼침 버튼

상세 영역에는 다시 다음 정보가 표시된다.

- 유형 변경
- 신뢰도
- 탐지 방식
- 동일값 일괄 처리

한 화면에 많은 후보를 표시하기 위한 설계 의도는 타당하지만, 지나친 압축으로 인해 사용자가 후보를 판단하기보다 UI를 해석해야 하는 문제가 생긴다.

### 핵심 문제 3. 체크박스 의미의 불명확성

현재 체크박스는 처리 대상 포함 여부를 의미한다. 그러나 사용자는 이를 다음 중 하나로 이해할 수 있다.

- 검토 완료 여부
- 개인정보 여부
- 처리 여부
- 목록 선택 여부

체크박스 대신 다음과 같은 명시적 상태를 사용하는 것이 좋다.

- 처리
- 제외
- 미확인

### 핵심 문제 4. 처리방식 선택상자의 반복

대부분 후보는 개인정보 유형별 기본 정책을 그대로 사용한다. 그런데 모든 후보 카드에 처리방식 선택상자가 반복 표시되어 시각적 소음이 커진다.

기본 정책을 적용하는 후보에는 처리방식을 텍스트로만 표시하고, 변경이 필요한 경우에만 상세 화면이나 메뉴에서 수정하도록 하는 것이 효율적이다.

### 핵심 문제 5. 문서와 후보의 연계 부족

후보를 선택했을 때 문서의 해당 위치로 이동하고 강조하는 기능은 있으나, 두 영역의 관계가 시각적으로 충분히 강하지 않다.

다음 반응을 강화할 필요가 있다.

- 후보 클릭 시 해당 문장으로 즉시 이동
- 선택 문장을 화면 중앙에 배치
- 주변 문맥을 함께 강조
- 후보 카드와 문서 강조 영역에 동일한 활성 상태 적용
- 현재 후보 번호 표시

### 핵심 문제 6. 유형 필터의 확장성

개인정보 유형이 많아질수록 필터 칩이 여러 줄로 확장된다. 사용자 정의 규칙이 추가되면 화면이 더욱 복잡해질 수 있다.

유형별 필터보다 다음과 같은 상태 중심 필터가 우선되어야 한다.

- 전체
- 확인 필요
- AI 발견
- AI 오탐 의심
- 처리 제외
- 수동 추가

개인정보 유형은 보조 필터나 드롭다운으로 제공하는 것이 좋다.

### 핵심 문제 7. 실행 전 동의 문구

현재 문구는 법적 동의처럼 읽힐 수 있다.

기존 의미:

> 탐지 결과를 검토하였으며 비식별 처리에 동의합니다.

권장 문구:

> 개인정보 후보와 제외 항목을 확인했습니다.

또는 별도의 최종 확인 단계에서 전체 처리 내역을 보여 주는 것이 더 적절하다.

## 4.4 결과 화면

현재 결과 화면은 다음 요소로 구성된다.

- 처리 경고
- 결과 요약
- 결과 파일 다운로드
- 처리결과 요약 다운로드
- 대응표 다운로드
- 대응표 보안 경고
- 처리 전후 비교
- 새 문서 처리
- 작업 종료

### 문제점

#### 다운로드 우선순위가 약함

실제 가장 중요한 결과물은 비식별 처리된 문서다. 그러나 결과 문서, 처리 요약, 대응표가 같은 줄에 배치되어 비슷한 중요도의 파일처럼 보인다.

#### 대응표 위험성이 충분히 구조화되지 않음

대응표에는 개인정보 원문이 평문으로 포함될 수 있다. 단순 경고 문구만 제공하기보다 다음과 같이 취급해야 한다.

- 기본적으로 생성하지 않음
- 사용자가 복원 필요성을 명시한 경우만 생성
- 생성 시 별도 확인
- 결과 문서와 분리 보관하도록 안내

#### 완료 상태가 약함

처리가 완료되었다는 성공 메시지보다 여러 패널과 버튼이 먼저 보이면 사용자는 작업 완료 여부를 즉시 파악하기 어렵다.

#### 전후 비교 방식의 한계

처리 전과 처리 후를 탭으로 전환하는 방식은 공간 효율은 좋지만 차이를 비교하기 어렵다.

권장 비교 방식은 다음과 같다.

- 변경된 항목만 보기
- 좌우 비교
- 전체 문서 보기

## 4.5 원본 복원 화면

현재 복원 화면은 비식별 문서와 대응표 파일을 선택한 후 복원하는 단일 패널 구조다.

### 문제점

- 민감한 기능인데 일반 탭처럼 쉽게 접근 가능
- 복원 불가능한 처리방식과 파일 형식이 설명문에만 표시
- 두 파일의 일치 여부가 실행 전 명확히 검증되지 않음
- 복원 가능한 항목 수를 사전에 확인하기 어려움
- 결과 파일이 어떻게 저장되는지 불분명함

### 개선 방향

복원 기능도 단계형 흐름으로 구성하는 것이 좋다.

1. 비식별 문서 선택
2. 대응표 선택
3. 파일 일치 여부 확인
4. 복원 가능 항목 확인
5. 복원 실행
6. 결과 다운로드

## 4.6 설정 화면

현재 설정은 다음 세 영역으로 구성된다.

- AI 탐지
- 유형별 기본 처리방식
- 사용자 정의 탐지 규칙

### 문제점

- 일반 사용자 설정과 고급 기술 설정이 혼재
- 변경 사항의 저장 방식이 명확하지 않음
- 설정 초기화 범위가 불분명
- 정규식 오류를 입력 전에 확인하기 어려움
- 조직 표준 정책을 저장하거나 공유하기 어려움

### 개선 방향

설정을 다음 세 개의 하위 메뉴로 분리한다.

1. 처리 정책
2. AI 엔진
3. 사용자 규칙

## 6. 새로운 비식별 처리 흐름

- 미확인 후보 수

- 부분 가림 수
- 토큰 치환 수
- AI 단독 후보 중 미확인 수
- 대응표 생성 여부

세부 검토와 최종 실행 사이에 요약 단계를 두면 실수를 줄일 수 있다.

## 7.3 검토 화면 개편안

### 권장 3열 구조

```text
┌──────────────┬──────────────────────────────┬─────────────────────┐
│ 검토 요약    │ 문서                         │ 개인정보 후보       │
│              │                              │                     │
│ 전체 124     │ [문서 내용과 강조 표시]      │ 검색...   필터 ▾    │
│ 미확인 12    │                              │                     │
│ 제외 4       │                              │ ┌ 후보 카드 ─────┐  │
│ AI 발견 8    │                              │ │ 김민수  성명    │  │
│              │                              │ │ 처리: 전체가림  │  │
│ 상태 필터    │                              │ │ AI 발견 · 확인  │  │
│ ○ 전체       │                              │ └────────────────┘  │
│ ○ 확인 필요  │                              │                     │
│ ○ AI 발견    │                              │                     │
│ ○ 제외       │                              │                     │
│              │                              │                     │
│ 유형 ▾       │                              │                     │
├──────────────┴──────────────────────────────┴─────────────────────┤
│ 112개 처리 · 4개 제외 · 8개 미확인     [처리 확인으로 이동 →]    │
└───────────────────────────────────────────────────────────────────┘
```

### 개편 핵심

#### 가. 왼쪽에 검토 요약과 상태 필터 배치

유형별 칩을 여러 줄로 표시하지 않고 다음 상태를 우선 제공한다.

- 전체
- 확인 필요
- AI 발견
- 오탐 의심
- 처리 제외
- 수동 추가

개인정보 유형은 하위 필터로 제공한다.

#### 나. 후보 상태를 명시적으로 표시

체크박스 대신 다음 상태를 사용한다.

```text
[처리] [제외]
```

검토가 끝나지 않은 후보는 미확인 상태로 둔다.

#### 다. 처리방식 선택상자 최소화

후보별 기본 정책은 텍스트로 표시한다.

```text
주민등록번호 · 기본 정책: 부분 가림
```

변경이 필요한 경우에만 상세 영역에서 수정한다.

#### 라. 후보 카드에 주변 문맥 제공

```text
┌──────────────────────────────────────────┐
│ 김민수                         [처리 ✓]  │
│ 성명 · AI 발견 · 신뢰도 중간             │
│                                          │
│ “계약 담당자 김민수 주무관에게…”          │
│                                          │
│ 적용 방식: 전체 가림           [변경]    │
└──────────────────────────────────────────┘
```

원문만 보여 주는 것보다 주변 문맥을 함께 제공해야 개인정보 여부를 빠르게 판단할 수 있다.

#### 마. 수동 후보 추가 방식 개선

기존 방식:

> 문장 드래그 → 상단 유형 선택 → 추가 버튼

권장 방식:

> 문장 드래그 → 선택 영역 근처에 팝오버 표시

```text
[성명으로 추가] [주소로 추가] [다른 유형…]
```

#### 바. 하단 진행 요약 상시 표시

```text
전체 124 | 처리 112 | 제외 4 | 미확인 8
```

미확인 항목이 남아 있으면 다음 단계로 이동하기 전에 명확히 경고한다.

## 9. 시각 디자인 개선 방향

## 9.1 유지할 기존 설계 원칙

현재 디자인 시스템의 다음 요소는 유지하는 것이 좋다.

- 4px 단위 간격 체계
- 제한된 글자 크기 단계
- 라이트·다크 색상 토큰
- 명확한 상태 색상
- 포커스 표시
- 최소 클릭 영역 고려
- 개인정보 유형을 과도한 색상으로 구분하지 않는 원칙

디자인 토큰 자체를 폐기하기보다 화면 구성과 컴포넌트 위계를 재설계하는 편이 효율적이다.

## 9.2 권장 브랜드 인상

safeDoc은 다음 이미지를 전달해야 한다.

- 안전함
- 정확함
- 차분함
- 공공·행정 업무 친화적
- 과도하게 기술적이지 않음

## 9.3 권장 색상 체계

| 의미 | 권장 색상 |
|---|---|
| 기본 행동·현재 선택 | 파랑 |
| 처리 완료·확인됨 | 초록 |
| 사용자 확인 필요 | 주황 |
| 개인정보 원문·위험 작업 | 빨강 |
| 제외·비활성 | 회색 |

개인정보 유형별 색상은 최소화하고 텍스트 배지를 사용하는 것이 좋다.

## 9.4 권장 글자 크기

현재 일부 도구 영역의 12~13px 글자는 장시간 검토 업무에 작을 수 있다.

권장 크기는 다음과 같다.

- 기본 본문: 15px
- 후보 원문: 15px
- 설명 및 보조 정보: 13px 이상
- 일반 버튼: 14px 이상
- 주요 화면 제목: 22~24px
- 패널 제목: 16~18px

## 9.5 버튼 체계 단순화

버튼 종류를 다음 네 가지로 제한한다.

1. **Primary**: 다음 단계, 실행, 결과 다운로드
2. **Secondary**: 일반 보조 행동
3. **Tertiary**: 텍스트형 보조 행동
4. **Danger**: 대응표, 복원, 데이터 삭제

버튼 크기와 시각적 무게를 화면마다 일관되게 적용해야 한다.

- 최종 처리 확인 화면 추가

- 1366×768

## 12. 결론

safeDoc은 기능 완성도와 접근성 기반이 우수한 개인정보 비식별화 도구다. 특히 규칙 기반 탐지와 로컬 AI 탐지를 결합하고, 자동 탐지 결과를 사용자가 직접 검토하도록 한 구조는 적절하다.

그러나 현재 UI는 전문 기능이 한 화면에 지나치게 압축되어 있으며, 사용자가 기능의 우선순위와 작업 순서를 스스로 해석해야 한다.

전면 개편에서 가장 중요한 방향은 다음과 같다.

1. 메뉴 중심에서 작업 중심으로 전환
2. 유형 중심에서 검토 상태 중심으로 전환
3. 모든 기능의 상시 노출에서 상황별 점진적 노출로 전환
4. 검토와 실행 사이에 최종 확인 단계를 추가
5. 민감한 대응표와 복원 기능을 일반 기능과 명확히 분리

특히 핵심 검토 화면은 다음 세 영역으로 재구성하는 것이 적합하다.

> 검토 현황·필터 / 문서 문맥 / 개인정보 후보 판단

이 구조를 적용하면 기능을 줄이지 않으면서 초보 사용자의 학습 부담을 줄이고, 숙련 사용자의 검토 속도도 높일 수 있다.

저장소 코드와 화면 구조를 기준으로 분석하였으며, 실제 브라우저 렌더링 화면의 픽셀 단위 시각 검증, 사용자 인터뷰, 클릭 추적, 사용성 테스트까지 수행한 것은 아니다.

실제 개편을 추진할 때에는 와이어프레임 제작 후 대표 사용자 5명 이상을 대상으로 다음 항목을 검증하는 것이 좋다.

- 첫 작업 시작까지 걸리는 시간
- 개인정보 후보 처리 여부 판단 시간
- 미확인 후보 누락률
- 대응표 다운로드 오인 비율
- 결과 파일 다운로드 성공률
- 키보드 사용자 작업 완료율
